# Collector → Backend Integration Contract

This document is the stable interface between the **Data Collection**
module (this repo's `collector/`) and the **Backend/API** module. Both
sides can develop and test independently against this contract without
waiting on each other.

## Overview

```
COLLECTOR                                   BACKEND
----------                                  -------
Input:  source content (HTML fixture,       Input: canonical Observation
        or later a real page)               JSON (one or many)

Processing:
  fetch → parse → extract → normalize       Endpoint:
  → validate                                  POST /api/v1/ingest/observations

Output: canonical Observation JSON          Processing: validate again
        (see schema below)                  (defense in depth), store in
                                             PostgreSQL, hand off to
                                             Neo4j/ML as needed

                                             Output: ingestion result
                                             (accepted/rejected counts +
                                             observation_ids)
```

The collector and backend are **not** in the same process and share no
code — the only thing that couples them is this JSON shape. Either side
can change its internals freely as long as this contract holds.

## Canonical Observation schema

| Field | Type | Required | Notes |
|---|---|---|---|
| `observation_id` | string | ✔ | Deterministic ID (`OBS_<16-hex>`), stable across re-runs of the same source/handle/content/timestamp. |
| `source_id` | string | ✔ | Identifies the source page/fixture this observation came from. |
| `timestamp` | string (ISO-8601 UTC, `...Z`) | ✔ | When the underlying event occurred (best-effort parsed from the source). |
| `observation_type` | string (enum) | ✔ | One of: `post`, `profile`, `listing`, `reply`, `message`, `identifier`, `infrastructure`, `wallet_reference`, `handle_change`, `migration_signal`. |
| `confidence` | float `[0,1]` | ✔ | **COLLECTION confidence, not actor-attribution confidence.** Heuristic score of how much structured evidence (handle/content/timestamp/PGP/wallet) was found on this one page. Says nothing about whether the evidence correctly identifies a real actor or links to other observations -- that's a separate, downstream score the backend/ML layer computes. Floor 0.3 / ceiling 0.95 by design (a single page should never claim near-certainty). |
| `actor_id` | string or `null` | optional | **Always `null` from the collector.** Actor resolution is a backend/ML responsibility, not a collection-time fact. |
| `handle` | string or `null` | optional | Handle observed on the page, if any. |
| `content` | string or `null` | optional | Free text content associated with the observation. |
| `pgp_key` | string or `null` | optional | Synthetic PGP identifier reference (`PGP_SYN_...`) if found. |
| `wallet_address` | string or `null` | optional | Synthetic wallet identifier reference (`WALLET_SYN_...`) if found. |
| `domain` | string or `null` | optional | Domain the source page belongs to. |
| `url` | string or `null` | optional | Source-relative URL/path for this observation. |
| `category` | string or `null` | optional | Free-text category, if determinable. |
| `language` | string | optional (defaults `"en"`) | ISO language code. |
| `first_seen` | string (ISO-8601 UTC) or `null` | optional | Currently mirrors `timestamp` at collection time. |
| `last_seen` | string (ISO-8601 UTC) or `null` | optional | Currently mirrors `timestamp` at collection time. |

This mirrors the field names already used in the project's synthetic
dataset (`02_observations.csv` / `DATA_DICTIONARY.md`) so the two data
sources can be joined/queried together without a translation layer.

## Backend endpoint expected

```
POST /api/v1/ingest/observations
Content-Type: application/json
```

### Expected response shape (backend team's call on exact wording)

```json
{
  "status": "accepted",
  "ingested": 1,
  "rejected": 0,
  "observation_ids": ["OBS_9c5c2176b9e64249"]
}
```

If some observations in a batch are rejected, the collector team's
expectation is a partial-success response (accepted ones stored,
rejected ones reported with a reason) rather than an all-or-nothing
failure — but the exact response contract is the backend owner's
decision; this is a proposal to align on, not a requirement imposed by
the collector.

## What the collector guarantees before sending data

Every observation that leaves `collector/validator.py` with
`is_valid = True` has already been checked for:

- all required fields present and non-empty
- `timestamp`/`first_seen`/`last_seen` are valid ISO-8601 UTC
- `confidence` is a float in `[0, 1]`
- `observation_type` is one of the allowed enum values
- the observation isn't entirely empty of intelligence content
- `pgp_key`/`wallet_address`, if present, match the project's synthetic
  ID formats (warning-level, not hard rejection, since real-world values
  may not match a fixed regex)
- `observation_id` is not a duplicate within the current collector run

The backend **should still validate again on its side** (defense in
depth) — the collector's validation is not a substitute for
backend-side validation, especially once a real (non-fixture) source is
introduced.

## Schema compatibility with the team's synthetic dataset

Verified by directly inspecting `02_observations.csv`'s header row (not
assumed): `observation_id,source_id,actor_id,handle,content,timestamp,
pgp_key,wallet_address,domain,url,category,language,observation_type,
confidence,first_seen,last_seen`. Every one of those 16 field names
exists in the collector's `Observation` schema (`schema.py`) with the
same meaning. Field **order** differs (cosmetic only -- JSON objects are
unordered; a CSV column order is not a contract). The collector adds no
field the CSV doesn't have, and is missing no field the CSV has.

This comparison is only as good as the one file inspected. It does
**not** confirm compatibility with `01_sources.csv`, `03_posts.csv`,
`04_identifiers.csv`, `05_infrastructure.csv`, `06_relationships.csv`,
`07_wallet_transactions.csv`, or `08_activity_timeline.csv` — the
collector doesn't currently produce data mapped to those files, so no
claim is made about them either way.

## Audit changelog (fixes made during the integration audit)

- Removed `email_alias` extraction entirely (was captured by the
  extractor but had no destination field in the canonical schema or the
  dataset it's meant to match — removed rather than silently dropped).
- `migration_signal`'s matched text is now folded into `content` when
  not already present, so the evidence is never lost regardless of page
  layout (previously only used as a boolean flag).
- Timestamp normalization now correctly handles timezone-offset
  timestamps (`+05:30`, `-04:00`, etc.) by converting to UTC; previously
  only bare `Z`/naive timestamps normalized correctly, and anything with
  a real offset silently failed validation.
- `observation_id` hashing now uses the full content string instead of
  a 200-character prefix, closing a real (if narrow) collision path
  between two different observations sharing a long common prefix.
- The "no timestamp found → use collection time" fallback is now logged
  as a warning every time it fires, so it's never a silent substitution.

## Git safety notes

Committed to Git (safe, non-sensitive):
- All of `collector/` (code + synthetic fixtures)
- `docs/COLLECTOR_CONTRACT.md`
- `examples/*.json`

Should be `.gitignore`d (not part of this repo's committed code):
- `.env` / credentials / secrets (none exist in this module currently)
- raw/uncontrolled scraped content (not applicable — no live fetching)
- log files, `__pycache__/`, local virtual environments
- machine-specific files (e.g. `.vscode/`, `.idea/`)

There is currently nothing sensitive in this module to ignore beyond the
standard Python/OS junk — no credentials, no real scraped data, no
proprietary API keys.
